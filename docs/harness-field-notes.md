# Harness field notes — external-repo dogfooding

## 2026-07-16 — ExampleGame build OOM hardening

A privacy-bounded inspection of the ExampleGame Pi sessions found 33 `build_project` calls across the three long July sessions. Six calls never produced a tool result; the interrupted calls ran for roughly 2.5–7 minutes before a resumed turn or session break, and user follow-ups explicitly reported repeated out-of-memory crashes. The pinned `.pi/project.json` supplied `cmake --build build --parallel` with no count. For a Unix Makefiles generator, bare CMake `--parallel` forwards effectively unbounded parallelism, unlike the project-preferred `.configure.sh`, whose `make -j$(nproc)` at least has a finite CPU bound. One missing-result call also overlapped a separate `-j2` unit-test build, confirming that available memory—not CPU count alone—must bound compiler concurrency.

Build Runner now plans native parallelism from cgroup/host available RAM, available CPUs, a reserve, per-job memory, project `maxJobs`, and a capped translation-unit scan. It rewrites bare or excessive CMake/Make/Ninja job flags to a finite count, defers critically low-memory starts, and reports the selected jobs. Configure scripts are inspected for build steps, accept pinned/per-call arguments, inherit the same limits (including an `nproc` shim), and suppress the old duplicate direct full build when the script already built the project. Regression fixtures cover the exact bare-`--parallel` shape, an 8-CPU/16-GiB large-repo plan, low-memory deferral, generated-tree exclusion, repository-owned default/target script arguments, and argument-free script defaults in a second repository.

## 2026-07-14 — Automation-loop retry and stale-delivery hardening

A privacy-safe scan of 1,392 Pi session files found five organic persisted automation loops but no completed loop state. The decisive signature was lifecycle misuse rather than state corruption: 27/28 loop-history records aligned with assistant provider-error messages, because the extension treated low-level `agent_end` retry attempts as completed iterations. Those false settlements consumed budgets, triggered stalls, and queued continuations behind retries; 16/17 eventually delivered prompts were already stale, while seven expected prompts never persisted. Promise-mode models also called the disabled tool completion path 16 times, producing avoidable contract errors; four later emitted the right tag only after the loop was inactive.

Hardened the loop around Pi's documented `agent_settled` boundary. Retry failures no longer enter settlement history; a provider failure that remains terminal pauses without consuming an iteration. Schema-v3 continuations now persist an opaque token bound to loop ID, prompt hash, and expected iteration, then a synchronous `input` gate accepts only the current token and drops inactive, wrong-session, advanced, duplicate, or legacy-stale deliveries. Pending tokens are invalidated on pause/cancel/completion and safely re-queued after interrupted session startup. Promise-mode `complete` calls return non-error exact-tag guidance, status reports the required completion action, and model-tool starts require explicit loop/autonomy intent from the current non-extension user input. Added fixed-enum settlement/stop-reason and queued/delivered/dropped telemetry without prompt text or raw tokens, plus retry/stale-delivery lifecycle coverage. The original happy-path mechanics—bounded budgets, evidence checkpoints, mode-0600 state, and managed `bg_run`/`run_deck` waits—remain intact.

Live verification caught a second lifecycle race before closure: an async `input` handler let print mode observe idle and dispose the session before the nested command turn started; after that was fixed, the same race appeared between `agent_settled` and its newly sent continuation. Input validation is now synchronous, async workspace/managed-work baseline refresh happens in `agent_start`, and both command and automatic sends keep their owning handler alive until Pi reports the nested agent run started. A real scratch-repo print-mode loop then ran iteration 1, delivered a token-bound iteration 2, detected the exact promise, persisted `completionMode=promise`, and exited rc=0.

## 2026-07-11 — Fifth session-mining round: Ralph-style task automation

The user's intended "loop" was the executable Ralph pattern evidenced by the Claude/glades-ml corpus, not only the recurring corpus miner from the prior round. Studied the installed official Claude Ralph plugin and the durable research artifacts from the long CHIRON program. Core mechanics: feed the same prompt after every settled turn; progress survives in files/git; stop on an exact completion promise or a bounded iteration budget. The successful research usage adds stronger operating rules: one measured bottleneck/change per iteration, cheap Gate-0 probes, explicit PASS/FAIL/NULL documentation, cumulative verified wins, and no retrying settled negatives. The iter-92 closure adds the critical safety boundary: pause when the next step needs long external waiting, credentials, strategic judgment, production retraining, or other resource authorization.

Implemented the Pi-native **Automation Loop** (`/loop`, `/ralph-loop`, `automation_loop`) with synchronous `agent_end` follow-up continuation (avoids print-mode stale-context teardown), default 20/max 500 iterations, exact `<promise>…</promise>` detection or evidence-backed tool completion, same-session isolation, per-iteration tool/error + hashed workspace/output progress, repeated-no-progress stall pause, prompt-file confinement, checkpoint/pause/resume/cancel controls, headless failure exit status, and ignored mode-0600 state under `.pi/automation-loop/`. Unlike `/goal`, it has no Hermes controller choosing new prompts: the task remains fixed and the workspace carries self-reference. Live scratch-repo proof: an exact-promise loop completed iteration 1 with rc=0 and persisted `completionMode=promise`; a deliberately incomplete `--max=2 --max-stalls=0` loop queued iteration 2, recorded two history entries, stopped `max_iterations`, and exited rc=1. The first live attempt also exposed a print-mode stale-context lifecycle trap; the confirmed path queues follow-ups synchronously in `agent_end`, starts through command `ctx.sendUserMessage`, and awaits `ctx.waitForIdle` only in print mode. See `docs/automation-loop.md`.

## 2026-07-11 — Fourth session-mining round: make the corpus a loop

The earlier rounds were high-value but manually scripted snapshots. Implemented `src/session-miner.js` + `scripts/mine-agent-sessions.js` and wired them into the reviewed Learning Loop Coordinator and `learning-dogfood` workflow. The scanner understands Claude/Codex/Pi JSONL, caches per-file aggregates by size+mtime, bounds the rolling window (30 days/newest 1 GiB by default), emits stable candidate/trend IDs, and converts candidates to at-most-once-per-UTC-day learning outcomes. Persisted state is aggregate-only: no transcripts/reasoning, prompts, raw commands/arguments/output, repo paths, or secrets; prompt-family fingerprints are salted HMACs. See `docs/session-mining-loop.md`.

First real baseline (live corpus while this session was active): **453 eligible sessions / 126.9 MB / 1,469 user turns / 10,158 tool calls / 244 tool errors (2.54%)** across 209 Claude, 1 recent Codex, and 243 Pi files. Incremental re-scan reused 452/453 files and read only 0.9 MB in ~55 ms. The report separated 71 explicit Claude `Skill` calls from 5,008 attribution events, found 116 normalized repeated-prompt groups (max family 233), 33 correction/persistence signals (2.25 per 100 user turns), and `Bash → Bash → Bash` 2,460 times across 143 sessions.

Stable candidates confirm that the new tools now need an adoption-measurement phase rather than more speculative surfaces: 2,348 legacy `tail`/`pgrep`/`nvidia-smi`/`sleep` calls vs `run_deck` 4; 531 `git status`/`git log` vs `repo_context` 0; 313 build rituals vs `build_project` 0; 156 `git diff` vs `gitevidence` 12. Tool-friction candidates remain for Pi `edit` (9/76 errors in the live window) and Claude `Write` (26/181). These are leads, not causal claims: later daily scans, reviewed proposals, delegated fixes, and falling rates/candidate clearance close the feedback loop.

## 2026-07-11 — Third session-mining round: the ML-training corpus

The corpus landscape shifted since the 07-10 rounds: ExampleGame data is pruned, Codex is dormant (one rollout since the mined history — a Graphviz `dot`-render → view-image → refine diagram loop, noted as a future visual-verification candidate), and the fresh never-mined material is **glades-ml/glades-trainer** (CHIRON 1B LLM training in C++98/CUDA): 19 Claude sessions (113MB, 423 clean human turns) + 10 Pi sessions (44MB), 2026-06-11..07-11. Adoption check: zero organic uses of the 07-10 workflow tools — expected, since no Pi sessions have run since they landed; the mined Pi sessions do use the older tools (`policy_enforcer` 159, `codegraph_*` 97, `create_subagent` 35), confirming tool-first delivery remains right.

- **#1 finding — run babysitting owns the corpus**: 59% of all human turns are training-run lifecycle ("Give a status report on the current run" 69x verbatim, 154x as a family; 18 more in Pi sessions). Each answer is a hand-built compound: `ls -td logs/*` logdir re-derivation (116x + ~150 scratch-pointer file ops), bounded `tail`+`grep` vitals parsing (795/1781x; step/val/loss/‖g‖/tok/s/skips/NaN), `pgrep` alive checks (338x), `nvidia-smi` (188x + 74x in Pi), bespoke until-grep poll loops rebuilt ~126x, with the naive sleep-poll form sandbox-blocked 8x. → Built **Run Deck** (`run_deck` tool; durable run registry, attach-by-log-pattern, vitals parser, bounded milestone watch, GPU digest, session-start injection).
- **#2 finding — research is experiment-shaped, the harness is bug-shaped**: every idea runs a pre-registered E0→E4 gate ladder with PASS/FAIL/NULL verdicts, GPU-hours, and ship/no-go closure, hand-tracked in ~170 Claude memory files; observed friction is wasted GPU-hours (redundant baselines, wrong-arm A/B, "are you running the multi-seed anyways despite what I said?"). → Built **Experiment Ledger** (`experiment_ledger` tool; pre-registered bars/arms, gate verdicts, run/commit links, closure decisions, session-start injection).
- **#3 finding — the learning loop was eating junk**: 23/33 verification proofs in this repo's own state (and 4/4 recorded learning outcomes) were `ok:false, verifiers:[], confidence:0` over an EMPTY change set — "nothing happened" scored as FAIL. → Fixed status semantics: empty change set = `not-applicable` (skipped by ingestion, counted as `skipped` in metrics), real change without verifier coverage = fail-closed `no-verifiers` ingested as `verification-coverage-gap`, real verifier failures unchanged.
- Also fixed: hermes-memory success paths now clear `lastError`, so the expected first-contact "No session found matching" probe no longer persists next to `lastRecallStatus:"ok"` and reads as a masked miss (found on 3 of 4 project state files); harness-awareness now teaches `run_deck`/`experiment_ledger`; the stale smoke-list assertion in `tests/codegraph-extension.test.js` (broken since the harness-awareness commit) is repaired.
- Verified live (headless `pi -p` in a fresh scratch repo): after `/run-attach logs/chiron*/run.log`, the exact mined prompt "Give a status report on the current run" was answered in one turn from injection + `run_deck` with correct parsed vitals (step 2500, loss 2.7210, val 2.7398, ||g|| 0.58, 25,120 tok/s, 1 skip) and an honest no-pid liveness caveat; after `/exp-open`, a fresh turn asked "is launching a baseline consistent with what was pre-registered?" recalled the bars/arms AND cross-checked the attached run against them (flagged val 2.7398 > 2.72 bar, 1 skip vs 0-skip bar) — exactly the drift-prevention the mining asked for.
- New open item from the live verification: concurrent headless `pi -p` turns against one fresh repo can hang after the command's work completes (three probes sat 20-90 min at zero output; a re-run under `timeout` showed `/exp-open` wrote its state instantly, then the process hung until killed). Suspected first-contact Hermes bootstrap contention; single sequential turns in the same repo completed in seconds before and after.
- **RESOLVED same day — headless hang root-caused and fixed.** Two compounding defects: (1) `runHermes` was built on `execFile`, whose timeout SIGTERM is advisory — a deterministic repro showed a TERM-ignoring hermes ran to completion and *resolved as success* 31s after a 300ms timeout, and `execFile` silently drops the `detached` option, so grandchildren inheriting the stdio pipes could keep the promise pending forever; in production this was the first-contact recall bootstrap (`hermes chat` mid-LLM-call), whose pending child handle kept the `pi -p` event loop alive 20-90 min after the turn ended. (2) Nothing cancelled background recall at shutdown — persistent state showed `lastRecallAt` written 10s *after* session quit even on the healthy path. Fix: `runHermes` rewritten on `spawn` with `detached` (own process group), a hard deadline that SIGKILLs the whole group and destroys the pipes at `timeoutMs + killGraceMs`, and the same group-kill on abort (spawn's own signal handling settles the promise mid-abort-dispatch and would skip the group kill — abort handling is ours); hermes-memory arms an unref'd `PI_HERMES_HEADLESS_LINGER_MS` (5s) abort of in-flight work when a headless session shuts down. Verified: unit repro (wedge + abort, no surviving grandchildren), full sweep + smoke green, and live — `pi -p 'say only ok'` in a fresh repo against a TERM-ignoring 30-min-hang fake hermes exited in 10.3s with zero zombie processes.
- Open candidates for a next round, evidence recorded: cognitive-automation injects a byte-identical ~6.7KB preamble per turn (237 repeats = 1.65MB in one session; also fires on 19/180 trivial `pi -p` one-shots) — inject once per session, delta after; policy-enforcer "write-like path outside repo" churn (196 blocks + 123 grants for legit sibling-repo/`~/.pi`//tmp writes) — workspace-trust allowlist; Pi's `edit` tool is the largest error source in the ML corpus (118 stale-`oldText` failures on >16k-line generated C++ files) — core-patch territory; `pi -p` rc=0 on failed work still needs an upstream mechanism; global runtime settings still marked 0.74.1 while patches pin 0.80.5.
- **RESOLVED next day (2026-07-11): injection dedup and `pi -p` exit codes.** Cognitive context is now injected once per content, not once per turn — identical blocks inject nothing and changes re-inject only the changed `###` sections; headless sessions get no cognitive injection by default (`PI_COGNITIVE_HEADLESS_INJECT=1` opts back in). Verified live: a gated headless one-shot injects zero cognitive-automation messages, an opted-in one injects exactly one. And the `pi -p` rc item needed no upstream mechanism at all — Pi print mode exits naturally, so `process.exitCode` set by an in-process extension survives (probe-verified: an extension setting 42 produced rc 42). `setTurnExitCode(ctx)` in the extension kit records the first nonzero code for headless sessions only; wired into `/verify-run` (FAIL → rc 1, PASS/not-applicable → 0, verified live both ways) and `/build`//`/test` (FAILED npm test → rc 1, ok → 0, verified live). Other commands can adopt the same helper.
- Also hardened while stabilizing the round's tests: bg-jobs records spawn failures on the job record (`spawn-failed` status) instead of an unhandled `error` event plus an indistinguishable "orphaned" job, and `run_deck watch` no longer trusts a single point-in-time liveness/log sample — a flake reproduced exit code 0 with the log not yet visible in the same millisecond; death is now final only when a completed job's log was actually read or death holds across two consecutive polls (15 consecutive full-suite sweeps clean, previously failing every ~1-12).

## 2026-07-10 — Sidecar "top half renders, bottom half blank" fix

Report: Pi as a tall side-pane chat (GNOME Ptyxis) renders fine when idle, but while a turn streams, content pins to the top half and the bottom goes blank, hiding the chat. Investigation: the patched renderer keeps completed turns in scrollback and manages only the active buffer; `renderVisibleViewport` (our scrollback-preserving resize path) painted `\x1b[2J\x1b[H` + the active buffer top-anchored — correct when content exceeds the window, but in tall windows with a short mid-stream buffer it blanked the lower half and wiped visible history. Reproduced deterministically at the engine level (fake terminal + ANSI emulation: content ended at row 12 of 46 after a mid-stream resize); real-pty streaming and resize captures (467/503/474 frames) plus a failed real-VTE attempt (GTK broadway segfaults headless) bounded the trigger to resize/forced redraws during streaming. Fix: pad blank rows above short buffers and model them as a negative viewport top (differential math is uniformly `screenRow = logicalRow - viewportTop`, and the post-write commit `Math.max(prevViewportTop, finalCursorRow - height + 1)` self-maintains the model). Verified: regression test green, end-to-end 46-row real-pi capture with three mid-stream resizes shows zero blank-bottom frames, apply script reconciles the regenerated patch cleanly. Restart/reload Pi to pick it up.

## 2026-07-10 — Session-corpus mining round (evidence-driven extension work)

Mined all three agent corpora statistically (no transcript dumps): ~/.claude/projects (670MB, all active since June, 95% ExampleGame), ~/.codex/sessions (2.8GB, 1,015 rollouts, 87% ExampleGame, historical), ~/.pi/agent/sessions (177MB). Key findings:

- **Pi usage is model-tool-driven, not command-driven**: slash commands are essentially never typed in Pi sessions (only `/subagent-run` x20); the used surfaces are model tools — `create_subagent` x123, `codegraph_*` x275, `policy_enforcer` x126, `evidence_binder` x38, `roadmap_update` x23. New capability must be tool-first; more command surface alone is dead weight.
- **#1 volume repetition — the build/test ritual**: `cmake --build` hand-typed 858x/month, project test binaries 1,043x/month (Claude corpus), configure→build→filtered-test in 49% of sampled Codex sessions; 35 builds/month killed by the 2-minute default timeout; 61 SIGABRT test crashes with 15 manual gdb sessions. → Built the **Build Runner** extension (`/build`, `/test`, `build_project`/`test_project` tools; pinned-or-detected commands, build-length timeouts, auto-backtrace on exit 134). Verified live: filter run, crash flagging, clean handling when gdb has no stack.
- **#1 human friction — the "still persists" spiral**: 40 recent + 148 historical "still persists"/"again" markers, 92 attached screenshots, the same bug message sent 9x in one day, 31 reverts; failed knob toggles (e.g. `P2T_RAGDOLL_KNOB_*`) retried across sessions. → Built the **Debug Ledger** extension (durable per-bug hypothesis→change→observation→verdict threads, session-start injection of already-tried changes). Verified live: a fresh session answered "what was already tried — do not retry that change" purely from injected context.
- Codex-era fan-out ritual (241-284 hand-pasted "Worker N" sessions executing subsystem-plan items) is largely superseded by native subagent tooling, but `create_subagent` x123 in Pi confirms the appetite; a plan→fan-out bridge remains a candidate for a future round.
- Claude-corpus tail: 177 "File has not been read yet" + 23 "modified since read" edit errors (35%+ of all tool errors) and heavy `cd`-boilerplate are Claude-harness-side frictions, noted but not Pi-extension material.

## 2026-07-10 — ExampleGame + ExampleML battery (pi 0.74.1)

Setup: 27 headless `pi -p` runs across two real repos — ExampleGame (119G C++ game repo, pre-existing `.pi/`) and ExampleML (2.7G Next.js app, clean first contact). Eleven status/workflow commands plus one real model task per repo; `/verify-run quick` and `/test-gaps` additionally on ExampleML. Zero network failures, zero timeouts. All status commands completed in 2.8–8.4s including session startup; real tasks 17–35s with grounded, accurate summaries.

### Fixed during/after this session

- **Stale-ctx background recall (hermes-memory)** — every headless turn's auto-recall died with "extension ctx is stale" (18 failures in the local log). Recall chain now snapshots `cwd` instead of holding ctx across up to 60s of Hermes work.
- **Stale-ctx agent_end handlers (trace-observability, learning-loop-coordinator)** — two "Extension error" banners on every `pi -p` turn: pi replaces the session at turn end, so agent_end handlers got a throwing ctx. Handlers now skip silently on stale ctx; `check-extensions-smoke.sh` gained a full-fleet headless turn that fails on any surfaced extension error.
- **Silent command output in headless runs** — nine commands (project-profile/index, doctor, doctor-hot-path, verify-plan, memory-map, codegraph-status, semgrep-status, test-gaps) produced zero stdout under `pi -p` with rc=0 because `ctx.ui.notify` output is dropped without a UI. The kit's `notify()` now falls back to stdout; swept across eight extensions.
- **Stale `.claude/worktrees` ingestion** — verify-run py_compiled files inside stale agent worktrees and test-gaps listed worktree duplicates as "existing tests". All four scanning libraries now ignore `.claude`.
- **Trace growth** — ExampleGame had accumulated 7.9GB of unrotated traces; the new `PI_TRACE_MAX_TOTAL_BYTES` retention (this repo, commit 9c4a405) reclaimed 7.6GB mid-battery. Working as designed; the accumulation predated the cap.

### Open friction

- **`pi -p` exit code is 0 even when a command's work fails** — `/verify-run quick` with two genuinely failing tests exits 0. Output is now visible (notify fix) so failures are at least greppable, but scripted use cannot rely on rc. Likely needs an upstream mechanism for commands to set turn exit status.
- **/goal-plan without Hermes auth** — fails with "Codex auth is missing access_token" (run `hermes auth`), dumps its ~1.4KB internal controller prompt as error output, repeats the remediation line twice, and still exits 0.
- **`.pi/` state is left untracked in target repos** — first contact with ExampleML created 2.1MB of `.pi/` state that shows as `?? .pi/` in git status; the harness never suggests ignoring it (e.g. via `.git/info/exclude`, which would stay repo-local).
- **Headless one-off turns mutate prior session state** — the battery silently deleted ExampleGame's pre-existing `.pi/roadmap/active.json` (completed-roadmap auto-clear treats any new user message as the clear signal, including unrelated `pi -p` runs).
- **Recall activity is invisible to traces** — hermes-memory logs only to `~/.pi/agent/hermes-memory.log`, so `/harness-metrics` cannot measure recall usefulness yet. Instrumenting recall start/hit/fallback as trace events would close this.
- Cosmetic: Markdown-only changes classified as `security, semantic` impact; hermes recall cache "age 45d" carries no staleness warning; `/learning-approve` takes only an id, so approval rationale has to go into the dismissal-style notes rather than the approve action.

### What worked well

- `/verify-run quick` derived correct verifiers from package.json on first contact and caught two real pre-existing test failures in ExampleML.
- Both repo-summary tasks read the right files (README/CLAUDE.md/main entry) instead of broad scans.
- `/obsidian-status` is the model for status output: state plus exact remediation knobs.
- Trace retention GC did its job at first opportunity.
